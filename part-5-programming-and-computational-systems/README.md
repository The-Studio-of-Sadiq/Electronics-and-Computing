# Part V — Programming and Computational Systems

Parts III and IV built the machine: logic gates, registers, datapaths, memories, processors and programmable logic, ending with hardware described in a language. Part V turns to the software that runs on that machine and the software engineers write around it. An electronics engineer today programs constantly: firmware in C or C++ for the microcontroller inside a product, Python for acquiring and analysing measurements and automating a test rig, and numerical code for simulating a circuit, a filter or a control loop before it is built. These programs have finite word lengths, memory and time, and their failures (an accumulator that stops counting, a pointer that outlives its buffer, a result that cannot be reproduced) are as real as a resistor that overheats. This part treats programming as an engineering discipline, with the same habit as the rest of the book: state the model, know where it holds, and measure the consequence.

## By the end of this part you should understand

- How an algorithm is specified and argued correct, and how variables, types, control flow, functions and data structures map onto the memory and time of a real machine.
- Where data live (static storage, stack, heap), how big each region must be on a microcontroller, and why firmware usually avoids dynamic allocation.
- How to organise code into modules, handle errors and faults deliberately, debug systematically and build test suites that run on every change.
- How C and C++ expose pointers, structure layout, bits, memory-mapped registers and the compiler-linker toolchain, and how embedded coding standards restrict them for safety-critical work.
- How Python, with NumPy, SciPy and Matplotlib, acquires, processes, plots and archives engineering data, and how to make a computational experiment reproducible.
- How to analyse the cost of an algorithm, choose a data structure for a task, and apply searching, sorting, numerical and graph algorithms to engineering problems.
- How scientific computing environments, matrix computation, data formats, parallelism, profiling, numerical precision, testing and version control fit together in a professional simulation workflow.

## How this part connects to the rest of the book

Part V stands on the hardware of Parts III and IV. The number representations of [Chapter 11](../part-3-digital-electronics/11-digital-number-systems.md) explain why a `float` accumulator freezes and why integer counters wrap; the processor, memory hierarchy and memory map of [Chapters 16](../part-4-computer-architecture-and-digital-hardware/16-computer-architecture.md) and [17](../part-4-computer-architecture-and-digital-hardware/17-microprocessors-and-microcontrollers.md) explain what a pointer, a stack frame or a cache-friendly loop really is; and the HDL of [Chapter 19](../part-4-computer-architecture-and-digital-hardware/19-hardware-description-languages.md) is the hardware counterpart of this software, with the same test discipline. Part V in turn feeds Part VI directly: the C, C++, memory, interrupt-safety and testing practice of Chapters 20 and 21 becomes the firmware architecture, interface drivers, real-time scheduling and hardware-in-the-loop validation of Chapters 25–28.

The mathematics behind the numerical work belongs to *The Mathematics Universe*: floating-point error analysis, root finding, interpolation, quadrature and ODE solvers in [Ch. 22](https://github.com/The-Studio-of-Sadiq/engineering-mathematics/blob/main/part-7-numerical-computational/22-numerical-methods.md), optimisation in [Ch. 23](https://github.com/The-Studio-of-Sadiq/engineering-mathematics/blob/main/part-7-numerical-computational/23-optimization.md), and numerical linear algebra, iterative solvers and Monte Carlo methods in [Ch. 24](https://github.com/The-Studio-of-Sadiq/engineering-mathematics/blob/main/part-7-numerical-computational/24-computational-mathematics.md). This part uses those results and adds word lengths, memory budgets, libraries, data formats and workflows. The signal-processing algorithms that Python analyses and C implements (sampling, the DFT and FFT, digital filter design) are owned by *Circuits, Signals and Communications*, [Part V](https://github.com/The-Studio-of-Sadiq/Circuits-Signals-and-Communications/blob/main/part-5-digital-signal-processing/README.md), and the discrete controllers coded in firmware by its [Ch. 35](https://github.com/The-Studio-of-Sadiq/Circuits-Signals-and-Communications/blob/main/part-7-control-system-fundamentals/35-control-design-fundamentals.md).
